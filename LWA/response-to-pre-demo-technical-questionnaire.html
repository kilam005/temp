Documentation (Waystar) Help

Response to Pre-Demo Technical Questionnaire

Deployment Model

Can your entire application stack... be deployed via Terraform or Helm directly into a customer-managed Google Cloud VPC?

Yes. The Central Manager and UI can be deployed centrally. The Execution Agents can be deployed via Helm side-by-side with your database workloads in different subnets/VPCs, dialing back to the manager.

Data Sovereignty & Network Path

Confirm that no data... leaves the customer VPC.

Confirmed. Data flows directly from the Source DB -> Local Execution Agent -> Cloud Storage via Private Google Access. The payload never traverses the Central Manager, keeping the control plane extremely light and ensuring absolute data sovereignty.

Metadata Storage

Does the platform support using a customer-managed Cloud SQL (Postgres or MySQL) instance for its internal application database and metadata catalog?

Yes. The Central Manager is built on Spring Data JPA and uses standard JDBC to connect to its metadata catalog. It fully supports being pointed at a customer-managed Cloud SQL instance (PostgreSQL or MySQL) simply by updating standard Spring datasource environment variables.

Identity Management

Does the platform support Google Cloud Workload Identity or service accounts for resource access, or does it require static IAM keys?

Yes. The platform fully supports Google Cloud Workload Identity. The Execution Agents running in GKE can be bound to Kubernetes Service Accounts (KSA) that reflect Google Service Accounts (GSA), allowing them to write to GCS and BigQuery without ever needing static, long-lived IAM keys.

Connectivity Model & Network Flow

Describe your connectivity model when the source networks cannot accept inbound connections.

Reverse-Connect / Polling Model. The Execution Agents are designed specifically for highly restricted networks. They operate on a polling/heartbeat mechanism (outbound HTTPS). They initiate an outbound connection to the Central Manager to fetch their job manifest, perform the local JDBC extraction and storage upload (push), and then post the results back to the Manager. No inbound traversal into the database subnet from the control plane is required.

Schema Drift & Type Changes

What is your behavior on rename, type change, or drop column?

Because extraction is driven by explicit JDBC queries against the source tables, the schema is read dynamically at the time of extraction. New columns are automatically appended to the resulting Parquet files. If a column is dropped or renamed at the source, the extraction query adapts dynamically, and the resulting Parquet schema simply reflects the new state for that batch. BigQuery external tables gracefully handle evolving Parquet schemas.
