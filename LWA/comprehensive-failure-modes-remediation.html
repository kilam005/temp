Given the distributed nature of the Archival Engine, the system is engineered with robust fault tolerance. The following matrix outlines the possible failure points across the Write-Verify-Purge pipeline, how they are caught, and the systemic remedy.

Yes (Manager pushes Job to another Agent).

If Agent died during Write/Verify, the Purge never ran; data is untouched. Next Agent restarts the extraction batch cleanly.

Source DB (JDBC)

Connection Refused

Incorrect credentials, IP not allowlisted in DB firewall, DB is offline.

Agent catches SQLException. Sends POST /job/failed payload to Manager.

Yes (Configurable up to 3 attempts, then fails).

UI highlights Job in RED. Administrator must fix DB credentials via Connection Profile.

Source DB (JDBC)

Deadlock / Timeout

High OLTP traffic locks the target table during the DELETE phase.

Agent catches SQLTimeoutException. Fails the specific batch transaction.

Yes (Agent enters wait-and-retry logic).

If retries exhaust, batch fails. Note: The data is now duplicated (in DB and GCS), but not lost. Job rerun will overwrite Parquet and re-attempt purge.

Archival Rule Execution

Invalid Policy Syntax

The user-defined WHERE clause (e.g., WHERE nonexistent_col < X) is invalid.

Agent catches syntax error on initial SELECT attempt. Reports immediate failure to Manager.

No (Deterministic failure).

Agent aborts before any writes happen. User must fix the Archival Policy in the UI.

Agent Execution

Local Disk IO Error

Node running the Agent runs out of ephemeral storage during local extraction buffering.

Agent catches IOException (No space left on device).

No (Agent aborts batch).

Step 2 (Verify) never happens. Next Agent picking up the job must have adequate ephemeral space to process the batch. DB data untouched.

Formatting engine

Parquet Type Incompatibility

A source column type cannot be serialized into the target Parquet schema (e.g. unknown proprietary DB object).

In-memory Parquet layout failure. Agent catches AvroTypeException.

No (Requires mapping fix).

Execution halts during extraction step. The system will not generate corrupt artifacts. Admin must update type mappings in Agent config. Database data untouched.

Target Storage

Write/Upload Rejection

Invalid GCS bucket, revoked GCP Service Account credentials, or storage quota exceeded.

HTTP 403/400 from GCS SDK. Agent catches exception during Step 1 (Write).

Yes (Transient network retries).

Agent aborts. Crucial: Step 2 (Verify) and Step 3 (Purge) are never reached. Source data remains perfectly intact.

Target Storage

Hash/Count Mismatch

The extracted Row Count/SHA-256 does not perfectly match the GCS Parquet metadata.

Agent deliberately raises VerificationException during Step 2.

No (Signals severe corruption or interception).

Agent explicitly aborts the Purge step. Alerts Manager of Critical Verification Failure. DB data untouched.

Job Reporting

Chain of Custody POST Fails

The Agent successfully Purges data, but the network drops before it can send the final JSON report to Manager.

Agent writes the JSON to a local persistent recovery file (/agent-data/recovery/).

Yes (Agent runs background sweep to retry sending).

The Archival succeeded. The Agent will infinitely retry sending the custody report to the Manager until the network restores, ensuring SIEM eventual consistency.
