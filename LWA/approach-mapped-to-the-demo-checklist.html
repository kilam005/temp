Approach mapped to the Demo Checklist

Multi-Server Management via Agents

You apply a policy to a target group of databases. The Manager dispatches the job payloads to the specific remote Execution Agents nearest to those databases.

Safe Purge & Cloud Integration

The remote Agent implements the strict Two-Phase Write-Verify-Purge workflow locally, verifies the Storage URI hash/ETag, performs the DB DELETE, and only then reports "Completed" parity to the Manager.

The below pointers are only theoretical at this point in time. We have to build this consideration to suit the solution. Read with caution.

  1. Multi-Server Management:

    • Demo Action: We will show a single "Archiving Policy" applied to a "Target Group" containing multiple SQL instances. The manager will broadcast 30 distinct jobs into the queue, automatically picked up by available connected agents.

  2. Complex Retention Logic:

    • Demo Action: We will configure a custom extraction query condition: WHERE COALESCE(closed_date, created_date) < [Threshold].

  3. Safe Purge Verification:

    • Demo Action: We will trace a single agent execution log. You will observe: 1) The SELECT statement, 2) The write to local buffer, 3) The successful HTTP/200 upload to GCS, 4) The generation of the SQL DELETE statement based on the extracted primary keys, and 5) The execution of that DELETE against the source DB.

  4. Schema Drift:

    • Demo Action: We will manually execute an ALTER TABLE ADD COLUMN mid-demo on the SQL Server. The next archiving run will automatically extract the new column, write it to the Parquet file, and we will demonstrate BigQuery querying the new column immediately.

  5. BigQuery Integration:

    • Demo Action: We will demonstrate the dynamic creation of an external table in BigQuery pointing to the hive-partitioned (year=YYYY/month=MM/day=DD) GCS bucket populated by the Execution Agents.

  6. Backpressure and Throttle:

    • Demo Action: We will demonstrate configurable batchSize and threadLimit settings on the Execution Agent, restricting how many concurrent JDBC connections and rows-per-minute the agent is allowed to extract, preventing DB DTU exhaustion.

  7. Failure Handling:

    • Demo Action: We will intentionally sever the network connection or kill the Agent process mid-upload. The Manager will detect the missed heartbeats, mark the job as FAILED (or ORPHANED), and requeue the job for another agent, cleanly demonstrating that the SQL DELETE was never executed for the partial batch.
