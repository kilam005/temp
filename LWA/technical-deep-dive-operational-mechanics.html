Technical Deep-Dive & Operational Mechanics

To provide complete clarity on the platform's operational flow and setup, the following mechanics define how the system coordinates.

Security, RBAC, and Audit Logging (SIEM Integration)

To ensure the centralized control plane is highly secure, the Manager employs a strict RBAC (Role-Based Access Control) model:

  • Users & Roles:

    • ADMIN: Full access to create Target Groups, assign Agents, and manage infrastructure profiles.

    • OPERATOR: Can only execute existing Archival Policies and monitor the Canvas UI.

    • AUDITOR: Read-only access to Job History and configuration.

  • Attributes & Groups: Users can be assigned to AD/LDAP Groups that restrict their visibility down to specific "Target Groups" (e.g., European Operators can only see and execute policies against European Databases).

Audit Tracking & SIEM Forwarding: Every action taken in the UI (e.g., User 'J.Doe' triggered Policy '7-Year-Purge' against Target 'DB-Prod-1') is captured in an immutable audit ledger. This ledger is formatted as structured JSON logs (stdout/sl4j) and automatically exported out of the Manager's Kubernetes pod via standard DaemonSets (like FluentBit or Datadog) directly into your centralized SIEM systems (e.g., Splunk, Google Chronicle).

Database Simulation Requirements

For the purposes of our demonstration and validation, we request that you provision:

  • 3 Distinct Relational Databases: (e.g., 2 SQL Server, 1 Postgres).

  • Scale Constraint: Please restrict each database to a maximum of 20 tables.

  • Sample DDL: If you do not have a test harness, you may execute the following generic DDL to create our demo target:

    CREATE TABLE demo_transactions ( tx_id INT PRIMARY KEY, account_id INT, amount DECIMAL(10,2), status VARCHAR(50), created_dt DATETIME, closed_date DATETIME ); -- Insert dummy records spanning the last 10 years.

UI Sitemap & Navigation

The Central Manager UI is designed for operational clarity, categorized into the following core sitemaps:

  1. Live Topology Canvas (Dashboard): The default landing page. Displays the real-time node-and-edge graphical visualization of Manager, Agents, Databases, and Storage targets with live data flow animations.

  2. Infrastructure:

    • Connection Profiles (Source DBs): Where JDBC credentials and network coordinates for your 100+ databases are stored.

    • Target Profiles (Storage): Where GCS Bucket URIs and GCP Service Account binding configurations are defined.

    • Agent Registry: A read-only list of dynamically registered Execution Agents, their host IPs, and last heartbeat timestamps.

  3. Policies & Execution:

    • Target Groups: Logical collections of Connection Profiles (e.g., "All North American Postgres DBs").

    • Archival Policies: The retention rules and extraction queries (e.g., "Purge older than 7 years").

  4. Job History: The audit log of all executed Write-Verify-Purge pipelines.

Target Groups & Target Profile Attachment

  • Target Groups: Target Groups are created purely logically within the Manager. You navigate to the UI, create a new cluster (e.g., "Production SQL Servers"), and assign existing Connection Profiles (Databases) to that group.

  • Target Profile Attachment: The Target Profile (the destination GCS bucket) is attached specifically to the Archival Policy (or the Job execution). Targets are independent of the Source DBs. The Agent simply needs to know where to read from (provided by the DB Connection) and where to write to (provided by the Policy target).

Archival Policies (Where do they run?)

An Archival Policy dictates exactly what rows qualify for destruction.

  • Example: WHERE created_dt < DATEADD(year, -7, GETDATE()).

  • Execution Locus: The policy logic is pushed down to the source database during extraction. The Manager injects this WHERE clause into the payload sent to the Agent. The Agent then executes SELECT * FROM [Table] WHERE [Policy_Logic] directly against the SQL Server. This guarantees the Agent only ever pulls data actively slated for archiving over the wire, radically reducing network IO compared to post-extraction filtering.

Agent Registration & Failover Mechanics

Agents are entirely stateless execution nodes. They are deployed via standard Kubernetes Helm charts (or Docker run commands).

  1. The 'Kill' Scenario: If an Agent process dies (OOM kill, host failure), it immediately stops sending its 5-second /api/agents/heartbeat ping.

  2. Manager Recovery: The Manager detects the missed ping, flags the Agent as DEAD, and transitions its active job backward from RUNNING to ORPHANED.

  3. Auto-Restart: Because the Agent is deployed via Helm/Kubernetes RepliaSets, the cluster will automatically restart the pod within seconds.

  4. Resumption: The newly spawned Agent generates a fresh UUID, registers with the Manager, and immediately begins polling. It simply picks up the ORPHANED job and starts the Write-Verify-Purge cycle cleanly.

The Reverse-Connect / Polling Model in Multi-Clustered Networks

To traverse highly restricted multi-clustered networks without requiring inbound firewall rules, the system relies on an outbound-only JSON polling loop.

The Agent wakes up every few seconds and sends an HTTP GET request to the Manager: GET https://manager.internal.corp/api/jobs/poll?agentId=agent-xyz-123

If a job is ready, the Manager immediately replies with the heavily structured extraction payload. Notice how the Agent is treated purely as a dumb terminal; everything it needs to know is provided dynamically.

Handling Multi-Table / Full Schema Extraction: When a Job is configured to archive an entire database schema or multiple tables, the Manager simply sends an array of tables within the source object. The Agent loops through this array, executing the policyFilter against each specified table.

{ "jobId": "J-98765", "source": { "driver": "com.microsoft.sqlserver.jdbc.SQLServerDriver", "url": "jdbc:sqlserver://10.0.5.55:1433;databaseName=ProdDB", "user": "archival_svc_acct", "tables": [ "demo_transactions", "demo_audit_logs", "demo_events" ], "policyFilter": "WHERE created_dt < DATEADD(year, -7, GETDATE())" }, "target": { "type": "GCS", "bucketUrlRoot": "gs://enterprise-archive-bucket/prod_db/", "format": "PARQUET" }, "constraints": { "batchSize": 10000, "threadLimit": 2 } }

By providing an array of tables, the single Job execution forces the Agent to iterate sequentially (or concurrently based on threadLimit). For each table, it generates the dynamic SELECT * FROM [table] statement, extracts the data to the bucketUrlRoot/[table]/, verifies the Parquet writes, and executes the independent DELETE FROM [table] commands.

Because the Agent initiates the connection implicitly out of the database tier, it effortlessly penetrates NAT gateways and egress firewalls to reach the central Manager. Once the Agent completes its Write-Verify-Purge loop for all tables in the array, it does a final POST back to the manager containing the hash match validation and the cumulative rows purged.

The Write-Verify-Purge Transactional Pipeline (Chain of Custody)

The core value proposition of the engine is that it treats data archiving not as replication, but as a rigid, failure-resistant transaction. To prove the Chain of Custody programmatically, here is exactly how the Agent executes this sequence against the orders table during the demo:

  1. Step 1: Write (Extract & Transform): The Agent executes the scoped SELECT against the database based on the assigned policy, buffering the records into memory.

    -- Programmatic Extraction Query executed by Agent SELECT * FROM orders WHERE order_dt < NOW() - INTERVAL '7 years' ORDER BY order_id ASC LIMIT 10000;

    The Agent immediately encrypts and writes these records directly to the target storage (e.g., uploading to GCS as highly compressed Parquet objects).

  2. Step 2: Verify (Cryptographic Hash & Row Match): Crucially, the database rows are NOT deleted yet. When uploading the Parquet object, the Agent calculates a SHA-256 cryptographic hash of the data stream. The Agent waits for the HTTP 200 OK from the Google Cloud Storage API, which returns the server-side calculated hash (ETag/MD5/CRC32c).

    The Agent strictly verifies two things:

    • The returned storage hash perfectly matches the local execution hash (proving no bits were flipped in transit).

    • The Parquet metadata row count perfectly matches the source extraction row count (e.g., exactly 10,000 rows).

  3. Step 3: Purge (The Safe Delete): Only after the Verification step computes a 100% cryptographic and volumetric match does the Agent generate the tightly-bound DELETE statements. It uses the exact Primary Keys it just secured in storage to execute the purge against the source database.

    -- Programmatic Purge Query executed by Agent (post-verification) DELETE FROM orders WHERE order_id IN (1, 2, 3, 4, ... 10000); -- (Only IDs explicitly confirmed in Step 2 are purged)

If the Agent crashes or the network drops during Step 1 or Step 2, the Purge is never executed. The transaction rolls back, and the data safely remains in the operational database until the Job is requeued. This explicitly guarantees a strictly verified Chain of Custody, completely eliminating the risk of "orphaned deletions" where data is purged from the DB but lost in transit to the archive.

The Chain of Custody Report (Reporting Hierarchy & Structure)

The reporting hierarchy is strictly Job Execution-specific. When an Archival Policy is triggered against a Target Group (a batch execution), it spawns a unique JobRun.

Immediately following a successful JobRun, the Agent generates an immutable Chain of Custody Report. This single report consolidates the results across all tables processed during that specific execution. This structured JSON payload serves as legal/compliance proof of the overarching transaction and is forwarded to the Manager (and subsequently to your SIEM/Splunk instance).

{ "jobId": "J-98765", "policyName": "7-Year-Purge", "executionTimestamp": "2026-03-01T14:22:01Z", "sourceDatabase": "PG-OMS-East", "agentId": "agent-xyz-123", "tableExecutions": [ { "table": "orders", "extractionQuery": "SELECT * FROM orders WHERE ...", "verification": { "rowsExtracted": 10000, "rowsPersisted": 10000, "payloadHash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e...", "storageHashMatch": true }, "purge": { "rowsDeletedFromSource": 10000, "status": "SUCCESS" }, "targetStorageUri": "gs://archon-demo-archive/orders/part-01.parquet" }, { "table": "shipments", "extractionQuery": "SELECT * FROM shipments WHERE ...", "verification": { "rowsExtracted": 5500, "rowsPersisted": 5500, "payloadHash": "8b1a9953c4611296a827abf8c47804d7e6c49...", "storageHashMatch": true }, "purge": { "rowsDeletedFromSource": 5500, "status": "SUCCESS" }, "targetStorageUri": "gs://archon-demo-archive/shipments/part-01.parquet" } ] }

Multi-Agent Execution & Aggregation: In large-scale deployments, a single Archival Policy might target a group of 50 databases, causing the Manager to dispatch 50 parallel tasks. If Agent A picks up the PG-OMS-East task and Agent B picks up the MSSQL-FIN-Core task, each Agent independently executes the Write-Verify-Purge pipeline for its assigned database and submits its specific JSON report back to the Manager. The Central Manager then aggregates these individual Agent reports into one final, highly structured Master Job Execution Report, providing a single pane of glass for the entire batch.

User Presentation & Exports: While the raw JSON structure is designed for programmatic parsing and SIEM ingestion, the Central Manager UI bridges the gap for human auditors. Navigating to the Job History tab allows IT and Compliance stakeholders to view this data visually and click to export the Job Execution report via two formats:

  1. Cryptographically Signed PDF: A formal, human-readable compliance certificate proving the mathematical guarantee of the data movement.

  2. CSV Summary: A flat table ideal for operational analysts to track archival metrics (Rows moved, Bytes saved) over time.
